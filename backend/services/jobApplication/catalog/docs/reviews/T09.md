## 安全缺陷与修复证据

根因链：root node_modules 的既有 Vite fs.allow → 新 workspace 目录链接 → Vite 按路径文本比较 → 后端源码可从链接请求读取。初始补充 fs.deny 可挡完整路径，但独立审查证实 Windows 8.3 别名仍能读取；首轮真实路径防护又漏掉 Vite module ID URL 的规范化。这些均是本地开发服务器文件边界问题，不是数据库读权限或 DTO 泄露。

最终由 `website/frontend/catalogFileBoundary.ts` 在 Vite 转换前处理 URL／module ID、现有 alias 和物理路径，按真实目录及最近存在祖先拒绝 catalog 文件；裸包 module ID 交由 Vite 自身 resolver 解析后判断，不加载模块。静态拒绝响应避免将错误堆栈广播给网页。保留默认敏感文件和 catalog 文本 deny 作为补充。该防护依赖可信本地主机，不声称处理恶意并发目录替换，也不替代生产部署隔离。

root 重现、修复及反例分别见 evidence 中 `T09-vite-shortname-before.json`、`T09-vite-canonical-after.json`、`T09-vite-module-id-after.json`。最终浏览器套件验证完整路径、workspace 链接、当前宿主真实短别名、raw/url/import、编码、module ID、source map 和不存在文件拒绝，前端客户端仍可读取。没有读取凭据文件。
